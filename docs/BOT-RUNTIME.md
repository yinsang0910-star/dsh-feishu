# 多人同时用：并发、@ 通知、引用回溯、插嘴判断、卡片

群里三个人同时发话，以前是一个跑完下一个才动；回复只往群里丢一句，群静音就没人知道；
选中一条旧消息（尤其带图的）说「你重新做这个」，机器人压根不知道「这个」是什么；
两个人聊得好好的，它突然插一句。

这些现在都改了。这份文档说清楚它现在怎么动、怎么调、怎么退。

## 一、并发：同一个人串行，不同的人并行

| 情况 | 以前 | 现在 |
| --- | --- | --- |
| 甲在跑，乙发话 | 排队等甲跑完 | 乙立刻开跑（还有空位的话） |
| 甲在跑，甲又发一句 | 排队 | 仍然排队——同一个人的任务必须按顺序，不然会话会被写乱 |
| 三个人的活都在跑，丁发话 | 排队 | 排队，但空出一个位就自动接上，不用再发一遍 |

- 默认上限 **3 个**同时在跑（`config.json` 的 `max_concurrent`）。
- 排队时会明说：`⏳ 现在 3 个任务同时在跑，这个排上队了，空出来自动接上。`
  同一个人排在别人后面时是 `⏳ 你前面还有 2 个在跑，这个排上队了，完了自动接上。`
- 为什么不是无限并发：agent 机是 600G2 那台小机器，一个任务就吃满一个模型连接，
  再叠额度也扛不住。3 是「够用且不炸」的值，机器换大了就往上调：

```jsonc
// /opt/feishu-bot/config.json
"max_concurrent": 3
```

改完 `systemctl restart feishu-bot.service`。想回到「一个一个来」就填 `1`。

进度卡的脚注会写 `在跑 2/3`，一眼看出现在是几路在跑。

## 二、回复 @ 发起人

群常年静音，不带 @ 的回复等于没回。现在：

- 群里：所有回复都带 `<at user_id="ou_xxx">`，被回的人手机上有红点。
- 私聊：不带 @（本来就有通知，@ 自己看着怪）。
- **结果卡也 @**：卡片的第一个元素就是 @ 那个人。卡片里用的是 `<at id=ou_xxx>`（卡片 markdown
  语法），文本消息用 `<at user_id=ou_xxx>`（富文本语法），两种写法不能混。
- **卡片是原地刷新的，刷新不推通知**。所以跑超过 30 秒的任务，除了刷新卡片，还会额外补一条
  短消息 `✅ 好了，在上一条卡片里（用时 1 分 20 秒）` 并 @ 他——否则他永远等不到提醒。

## 三、引用/回复一条旧消息

你按住某条消息「回复」再说「你重新做这个」，飞书事件里只带一个 `parent_id`，正文和图片都不在里面。
以前机器人拿不到，只能接着当前上下文瞎猜——你让它重做，它把上一轮的结论又贴一遍。

现在会**先回去把那条消息捞出来**：

| 被引用的是 | 机器人看到什么 |
| --- | --- |
| 文字 | 原文（最多 1200 字）+ 你这句话 |
| 图片 | **把那张图下载下来落到工作区**，跟直接发图走同一条路，模型真的用 `read_image` 打开看 |
| 文件 / 视频 / 语音 | 同样下载落盘，交给模型处理 |
| 富文本（post） | 拍平成文字，图记成 `[图片]` |
| 卡片（比如上一轮的结果卡） | 拍平成文字，能读到上一轮的结论 |
| 表情包 | `[表情包]` |

拼出来的任务长这样：

```
【用户发来一张图片，已存到工作目录】.feishu-inbox/img-20261101-131502.jpg（相对 /home/agent/work/…）

他附言：【他引用了（咪咪 发的）的一条图片消息，下面这张就是】

【他这句话】你重新做这个
```

拿不到那条消息（被撤回、太旧、没权限）时，会老实说一句「取不到」，不会装作看见。

**实测**：清空会话（`session=None`，没有任何上下文）后引用一张试卷照片问「什么科目」，
12 秒答「有机化学」——只能来自真的打开了那张图。

## 四、什么时候不该接话

群聊免 @ 之后（见 [BOT-GROUP-MODE.md](BOT-GROUP-MODE.md)），机器人会听到群里每一句话。
它得判断「这句是不是在使唤我」，否则就会在两个人互相接话时插嘴。

判定顺序（`_chatter_reason()`，只对群里没 @ 机器人的消息生效）：

| 情况 | 接不接 | 原因 |
| --- | --- | --- |
| 回复的是机器人的消息 | **接** | 那就是给我看的 |
| 回复的是别人的消息 | 不接 | 两人在对话 |
| @ 了别人（没 @ 我） | 不接 | 点名的是别人 |
| @ 了我和别人 | 不接 | 主语不明确，宁可少接 |
| 谁也没指向 | **接** | 默认当作在使唤我 |

两个容易踩的坑，都已经处理：

- **机器人发的消息，sender 是应用（`cli_…`）不是 open_id（`ou_…`）**。只比 open_id 会把
  「用户回复我的结果卡」误判成「回复别人」，于是该接的不接。`_is_me()` 两个都认。
- **取不到被引用的消息**（撤回、太旧、id 无效）时，按「回复的是别人」处理 —— 保守不接，
  而不是当成「谁也没指向」抢着回答。

## 五、让它停手

「你别乱搞」「这不是你要管的」「别弄了」这类话，如果照原样派给 agent，它会真的去「处理」一遍
（实测跑 8 分钟还没完），既插嘴又白烧一次额度。

现在在派发之前就拦下来（`STOP_WORDS`，只在整句 ≤30 字时生效）：

- 他名下还有任务在跑 → 发中止信号，回一句「好，停了。」
- 没有在跑的任务 → 回一句「好。」

词表刻意收得很窄（`别改`、`别动了` 这类会被误伤的组合没有收），因为
「别改代码，只跑测试」是正常指令，不能拦。

## 六、卡片：一句话只该有一张卡

一句话最多产生两条消息：**一条进度卡**（原地刷新）+ **一条「好了」的短提醒**（只在任务跑超过
30 秒时发，因为卡片原地刷新不推通知）。回答永远回填到那张进度卡上，不另起一条。

三条实现约束：

- **进度卡只留最近 3 步**（`build_progress_card` 里的 `tail = task.steps_log[-3:]`）。
  列满屏没人看，还把任务正文挤没了。
- **结果一律用卡片**（`build_final_card`，`lark_md` 能渲染加粗、代码、列表）。
  卡片 patch 失败时新建一张结果卡，而不是退回 `deliver()` —— 那是纯文本消息，
  markdown 不渲染，就是一坨灰底。只有新建也失败（比如飞书侧 5xx）才退回 `deliver()`，
  此时宁可发纯文本也别把结果丢掉。
- **刷新节流 2 秒**（`refresh_progress`），避免撞飞书限频。

### 通道模式（`channel_mode`）现在是关的

2026-11-04 加过一版「通道模式」：消息不 spawn 子进程，而是投给 agent 机上常驻的
`dsh-feishu-channel` 插件，由 DSH 在轮次/step 边界领取 —— 换来「插话」「/下一轮」「流式」。

它带来三个问题（第 1 条已经修了，第 2、3 条还在），所以默认关掉（`config.json` 里 `channel_mode: "off"`）：

1. **同一句话两张卡**：`ingest` 超时后无条件退回老路径，而插件其实已经接单 →
   插件卡 + 老路径进度卡同时在。日志里能看到
   `通道投递失败，退回老路径：TimeoutError /ingest: timed out` 紧跟着 `task start`。
2. **卡片由插件生成**，样式与老路径不一致：思考流水逐条列、7 步全列，又长又密。
3. **慢**：插件侧要等轮次落定才推 `reply`，比直接收子进程输出慢一截。

第 1 条已经修了：`send_via_channel` 把 ingest 包成 `_ingest()`，超时后**用同一个 msgId
重投一次**（插件按 msgId 幂等，重复投递回 `duplicate=True`），两次都失败才退老路径；
`channel.py` 的 `DEFAULT_TIMEOUT` 也从 20 秒放宽到 45 秒。现在开通道不会再撞出双卡。

想再试：`channel_mode` 改 `"on"` 并重启（`channel.py` 与 `send_via_channel` 都还在）。
仍然要接受的是第 2、3 条：插件卡片会逐条列思考流水，且比老路径慢一截。

## 七、只发一个 @ 怎么办

飞书里常见操作是：先打字发出去，再补一条只有 `@机器人` 的消息。原来这会得到一句
「在。直接说要做什么就行」，因为清洗完 `@` 之后正文是空的。

现在 `handle_inner` 会记住每个人在每个会话里说的上一句（`_LAST_MSG`，**60 秒**内有效），
只发 `@` 时接上那句。两种写法都认：

- 飞书 @ 组件给的占位符 `@_user_1`（事件里的真实形态）
- 手打的 `@G2 Agent`（`BOT_NAME` 从 `/bot/v3/info` 取，去掉之后只剩 `@` 和空白就算「没打字」）

## 已知边界

- 一次只跟一条引用走：引用的消息里如果再套一条引用，只还原第一层。
- 被引用的图片仍然受 20MB 上限（`max_attachment_mb`）和 `.feishu-inbox/` 沙箱约束。
- 卡片 @ 用的是被回那个人的 `open_id`；他改过昵称不影响。
- 插嘴判断只看「回复对象」和「@ 了谁」，不看语义。两个人聊到一半突然说「帮我查一下」
  （既没回复谁也没 @ 人），它还是会接 —— 这是「免 @」的代价，想彻底避免就 `/要@`。

## 怎么退

这几件事都在 `services/feishu-bot/bot.py` 一个文件里，回滚整个文件即可：

```bash
cp -p /opt/feishu-bot/bot.py.bak-before-at /opt/feishu-bot/bot.py
systemctl restart feishu-bot.service
```

只退并发：把 `max_concurrent` 改成 `1`，重启。
只退 @：删掉 `handle_inner` 里的 `reply()` 包装，把调用换回 `send(chat_id, …)`（45 处）。
只退引用：删掉 `handle_inner` 里 `quote_note` 那一段。
只退插嘴判断：删掉 `handle_inner` 里 `_chatter_reason` 那个 `if` 块。
只退停手：删掉 `STOP_WORDS` 那个 `if` 块（「停」命令仍然有效）。
只退卡片瘦身：把 `tail = task.steps_log[-3:]` 改回 `[-5:]`。
只退「@ 接上文」：删掉 `_LAST_MSG` 那两段（记录 + 接上一条）。
想回通道模式：`channel_mode` 改 `"on"` 重启（会带回双卡与思考流水，见第六节）。
